Chapter 4

The Process Abstraction

Defines the vocabulary used everywhere else in the module. Know every term below cold.

4.1Program vs. process

A program is a static executable sitting on disk — just bytes. A process is a running instance of that program, managed by the OS. Two processes can run the same executable and still be entirely distinct (different PIDs, registers, stack, address space, PCB).

4.2Machine state the OS must preserve

  • Address space — code, data, heap, stack.
  • Registers — including the program counter (PC) and stack pointer (SP). These say exactly where execution was and must be restored to resume correctly.
  • Open files and other I/O state.

Common trap: a process waiting on I/O must be blocked, not ready — marking it ready would let the scheduler pick it even though it cannot make progress yet.

4.4The Process Control Block (PCB)

Plain English: think of the PCB as an index card the kernel keeps for every process it's managing. Whenever the OS needs to know "what is this process doing right now, and where do I go to give it the CPU again?" — it reads that card. Every process gets exactly one card, and the kernel updates it constantly.

Concretely, the card (a per-process table entry the kernel maintains) contains: PID, current state, saved register context, scheduling info, parent relationship, memory info, and open files. It lives in the kernel — not in the executable file on disk — because it describes one specific running instance and changes every time that process is paused or resumed. The executable file, by contrast, is just static bytes and never changes while the program runs.

4.5Two recurring distinctions

  • Time sharing vs. space sharing — the CPU is time-shared (one process at a time, switched rapidly); physical resources like memory or disk are space-shared (divided among processes at once).
  • Mechanism vs. policy — mechanism is the low-level machinery that makes something possible (e.g. "the OS is capable of saving one process's state and loading another's" — a context switch). Policy is the decision layered on top of that machinery that decides when/which to use it (e.g. "given that we can switch, which process should we switch to?"). A useful test: if you swapped out the decision-making logic but kept the underlying machinery working the same way, you changed the policy, not the mechanism. This split recurs constantly in Ch 6 and Ch 7.
P1 connection. proclab creates multiple processes that each move through this exact state diagram. A worker that has exited but hasn't been reaped sits in the terminated / zombie state. Polling /proc/<pid>/stat is literally reading the state the kernel tracks in the process table — the character Z corresponds directly to "terminated" here.
Study prompt: ask an AI for four statements about ready/running/blocked/terminated where at least one is subtly wrong, and evaluate each one yourself before checking. That's exactly the combinational-MCQ skill.
Chapter 5

The Process API

This chapter maps directly onto P1. Expect detailed fork/exec/wait questions and code-assembly blocks built from P1-like code.

5.1fork()

  • Called once, returns twice — once in each process.
  • Parent: returns the child's PID (positive).
  • Child: returns 0.
  • Error: returns a negative value; no child was created.
  • Parent/child output order after fork is nondeterministic without explicit synchronization — the scheduler decides who runs first.
  • The child inherits a copy of memory including stdio buffers. If both processes flush inherited buffered output, you can get duplicate output — this is the root of the exit()/_exit() trap below.
Always check fork()'s return value — assuming success (rather than handling the −1 case) is a common near-duplicate code-assembly bug.

5.2exec() family

  • Replaces the calling process's program image (code, data, heap, stack) — but preserves the PID. It is not a new process.
  • On success, exec() never returns — the new program starts running in its place. Any code written after a successful exec() call is therefore the failure path only.
  • On failure, exec() returns and you should report the error and exit (proclab uses _exit(127) here — see below).

5.3exit() vs. _exit() — the #1 code-assembly trap

exit()_exit()
Runsatexit handlers + flushes stdio buffersterminates immediately, no cleanup
Risk after fork()flushes inherited buffered output → can duplicate parent's outputsafe — nothing inherited gets re-flushed
Rule of thumb: in a forked child's failure path (e.g. exec failed), use _exit(), not exit(). Your proclab.c does exactly this: _exit(127) after a failed execl().

5.4wait() vs. waitpid()

  • wait(&status) — collects any eligible child. If a parent owns multiple children, it might reap the wrong one relative to the order you wanted.
  • waitpid(pid, &status, 0) — targets a specific PID. Required whenever the parent must process children in a specified order (exactly proclab's requirement — it reaps by index, in order).
  • Returns the reaped child's PID on success.

5.5Decoding exit status

  • The status integer from wait()/waitpid() is encoded — it is not the exit code itself. It can represent normal exit, signal death, and more.
  • WIFEXITED(status) — true if the child exited normally. Check this first.
  • WEXITSTATUS(status) — only meaningful/valid once WIFEXITED is true; extracts the actual exit code.
Trap: using the raw status value as if it were the exit code, instead of extracting it with WEXITSTATUS() after confirming WIFEXITED().

5.6Zombies, and what "reaping" actually means

Plain English — zombie: a child process finishes running, but the OS can't fully delete it yet, because the parent might still want to know how it finished (did it succeed? what exit code did it return?). So the kernel keeps just enough of a record behind — like a receipt — until the parent comes to collect it. That leftover, not-yet-cleaned-up record is a "zombie." It isn't doing anything spooky: it's not running, using CPU, or taking any action at all. It's just an unread receipt sitting in the kernel's process table.
Plain English — reaping: "reaping" is simply the parent calling wait()/waitpid() to read that receipt and then throw it away. The parent finds out the child's real exit status, and the kernel deletes the leftover table entry. Once reaped, the zombie is fully gone — there is nothing left to look up.

So the full sequence for any one child is: it runs → it exits → it becomes a zombie (finished, but its receipt is still on file) → the parent reaps it (reads the receipt, receipt is destroyed). A zombie consumes no CPU and runs no code — the kernel just keeps a minimal process-table entry around (PID, termination state/status) so the parent has something to read. waitpid() is what destroys that entry, and it only does so after it succeeds.

Why observation must happen before reaping. The instant waitpid() succeeds, the receipt is gone — the /proc/<pid>/stat entry disappears along with it, so you can no longer look it up and confirm "yes, this was a zombie." That's why proclab first polls /proc/<pid>/stat until it sees state Z for every child, and only then starts reaping. Reap first and you'd destroy the evidence before you ever got to check it.

5.7/proc/<pid>/stat

Exposes kernel-tracked process name and state to user space. Key state characters: R running, S sleeping, Z zombie.

Bounded polling beats a fixed sleep. A fixed sleep() proves nothing about whether a child has actually reached the zombie state — it's a guess. Polling /proc/<pid>/stat on an interval with a timeout is evidence-based observation. Proclab polls roughly every 5 ms with a ~2s total timeout.

5.8Cleanup on partial failure

If some children were created before something failed (e.g. the 3rd fork() fails after two succeeded), the parent must still reap the children it did successfully create — never leave processes or zombies orphaned.

5.9Full code-assembly trap list (Ch 5)

  1. exit() vs _exit() in the child after fork()
  2. wait() vs waitpid()
  3. using raw status vs WEXITSTATUS() after checking WIFEXITED()
  4. checking fork()'s return value vs assuming success
  5. reaping before observing vs observing the zombie state first

Chapter 6

Limited Direct Execution

How the OS runs processes at near-native speed while never losing ultimate control.

6.1Direct execution & why it must be limited

Direct execution = run user code straight on the CPU rather than interpreting it — this is what makes processes fast. But unlimited direct execution is unsafe: a process could issue privileged operations, access arbitrary memory, or simply never yield the CPU.

6.2User mode vs. kernel mode

Privileged operations (I/O, memory management, etc.) are restricted to kernel mode. Ordinary application code runs in user mode and must cross into kernel mode to do anything privileged.

6.3The system call path

libc wrapper
→
trap instr.
→
mode switch → kernel
→
kernel handler
→
return-from-trap → user
Plain English: your program can't just reach into the kernel and start running kernel code — that would let any program do anything, including dangerous things. Instead it executes a special trap instruction, which is like ringing a doorbell: it forces the CPU to switch to kernel mode and jump to a pre-registered handler at a location the kernel chose, not one the user program chose. The kernel does the privileged work on the process's behalf, then a "return-from-trap" hands control back to the user program in user mode, right where it left off.

A system call looks like a C function call but is semantically different: it crosses a privilege boundary via a trap instruction, rather than just jumping to different code in the same privilege level.

6.4Cooperative vs. timer-driven control transfer

  • Cooperative — the process voluntarily traps into the kernel (system calls, faults, exit()).
  • Timer-driven preemption — the hardware timer fires and forces a trap, regardless of what the process is doing.
Why the timer matters: without it, a CPU-bound process making no system calls would never return control to the OS. Purely cooperative scheduling can't guarantee the OS regains control.

6.5Context switch

The OS saves the running process's registers/state, restores the next process's saved registers/state, and switches address spaces.

  • Direct overhead — the actual save/restore work.
  • Indirect overhead — cache and TLB effects from switching working sets.

6.6Mechanism vs. policy, concretely

The context switch itself is a mechanism (the "how" of switching). The scheduling algorithm that decides which process to switch to is a policy. Same split for: timer interrupt = mechanism (regain control); scheduler's choice = policy (what to do with that control).

P1 connection. Every fork(), exec(), waitpid(), and _exit() in proclab is a controlled trap into the kernel. With multiple children running, the timer interrupt + scheduler decide which child (or the parent) runs at any instant — proclab produces deterministic output despite this nondeterministic interleaving only because the parent explicitly synchronizes (polling, then waiting) instead of assuming any particular execution order.
Study prompt: list five OS items — trap, timer interrupt, context switch, ready queue, Round Robin, page table — and classify each as mechanism or policy, explaining why.
Chapter 7

Scheduling: Introduction

Know every algorithm well enough to build a timeline and compute metrics by hand.

7.1Core definitions

MetricFormula
Turnaround timecompletion time − arrival time
Response timefirst run time − arrival time
Trap: completion time and turnaround time are the same number only when every job arrives at time 0. If arrivals differ, you must subtract arrival time.
Trap: response time measures time to first service, not time to completion and not "first printed output."

7.2FIFO (First In, First Out)

Runs jobs strictly in arrival order, to completion, non-preemptive.

Convoy effect: a long job that happens to arrive first delays every shorter job stuck behind it — badly hurting average turnaround.

Example (A=12,B=3,C=5, all arrive t=0): 0–12 A, 12–15 B, 15–20 C → avg turnaround = (12+15+20)/3 = 15.67

7.3SJF (Shortest Job First)

Non-preemptive. Always picks the ready job with the shortest total CPU demand. Minimizes average turnaround under its assumptions: simultaneous arrival + known job lengths.

Trap: "SJF is always optimal" is false — optimality depends on those assumptions holding. Real interactive workloads violate both (jobs arrive continuously, lengths aren't known in advance).

Same jobs, SJF: 0–3 B, 3–8 C, 8–20 A → avg turnaround = (20+3+8)/3 = 10.33

7.4STCF (Shortest Time-to-Completion First)

The preemptive version of SJF. At every arrival, compares remaining time (not original length) and preempts the running job if the new arrival is shorter. Handles staggered arrivals.

Trap: STCF compares remaining time, not arrival order and not original job length.

7.5Round Robin

Each ready job gets a fixed time quantum, then the next ready job runs — cycling through repeatedly. Improves response time dramatically; typically hurts average turnaround relative to FIFO/SJF because no job finishes early.

  • Quantum too small → excessive context-switch overhead eats into useful throughput.
  • Quantum too large (≥ every job's demand) → Round Robin degenerates into FIFO behavior.
Trap: Round Robin does not "prioritize" interactive jobs specifically — it gives all ready jobs equal, repeated turns. It helps interactive workloads only because it lowers response time generally.

7.6Policy selection has no universal winner

No policy is "best" without naming a workload and an objective. Interactive/short-request workloads (want low response time) → Round Robin. Batch/known-length workloads (want low turnaround) → SJF/FIFO. Context-switch overhead and I/O overlap both matter qualitatively: overlapping an I/O-bound job's wait with a CPU-bound job's computation improves total system throughput versus running everything sequentially.

P1 connection. proclab's children compete for the CPU under whatever policy the OS actually uses (Linux: CFS). The parent can't predict which child the scheduler runs first — which is exactly why proclab must synchronize explicitly (poll, then waitpid) instead of assuming a fixed order. Same binary, different run, different interleaving — but deterministic output.

Study prompt: for a given workload, build the FIFO, SJF, STCF, and RR timelines by hand and compute average turnaround + average response for each before checking your work.

Assignment 1 Ch 4 · Ch 5 · Ch 6

A1·Q1Program, process, and process state

Q: Name three parts of process machine state the OS preserves; what a PCB contains and why the kernel (not the executable) holds it; why two processes running the same executable are still distinct.

A: (a) Address space, CPU registers (PC, SP), and open-file/I/O state. (b) A PCB holds PID, state, saved registers, scheduling info, parent relationship, memory info, and open files — kept in the kernel because it describes one running instance and changes constantly, while the executable only holds static code/data. (c) Different PIDs, separate registers/PC/stack/address-space mappings/state/PCB, even from identical starting bytes.

A1·Q2Process-state transitions

Q: Ready → scheduled → runs → blocking read → resumes → preempted. List the transitions; why "ready" (not "blocked") would be wrong during the read; what moves it out of blocked, and is it guaranteed to run next?

A: ready → running → blocked → ready → running → ready. Marking it ready during the read would let the scheduler pick a process that still can't make progress. An I/O-completion interrupt moves it blocked → ready; it's not guaranteed to run immediately — the scheduler chooses among all ready processes.

A1·Q3Reasoning about fork()

Q: PID 410 forks (child PID 411); child does value += 2, parent does value += 5, starting value = 8. What prints, why can the two differ, and can the order be determined?

A: Child prints child: rc=0 value=10; parent prints parent: rc=411 value=13. They differ because fork() gives the child a logically separate address space — each modifies its own copy. Order is not determinable from the code alone; with no synchronization, the scheduler decides which reaches printf() first.

A1·Q4Process replacement and failure handling

Q: Child calls execl(). What happens to code/data/heap/stack/PID on success? Why doesn't code after a successful exec run? Why is _exit(127) safer than exit(127) after a failed exec?

A: Code/data are replaced, heap/stack reinitialized — but the PID stays the same (not a new process). Code after a successful exec never runs because success means execution jumped into the new program, not a return. _exit() skips flushing the child's inherited stdio buffers, avoiding duplicated output that exit()'s cleanup could cause. 127 conventionally signals "could not execute."

A1·Q5Zombies, observation, and reaping

Q: Parent creates three children, must confirm each is a zombie before collecting any. What remains during zombie state? Why check /proc before waitpid()? Why waitpid(pid,&status,0) over bare wait() for ordered processing? How are WIFEXITED/WEXITSTATUS used?

A: The child has finished (no CPU use); the kernel keeps a table entry with PID, termination state, and encoded status. A successful waitpid() reaps the child and lets the kernel remove that entry — so all observation must finish before the first reap, in a separate pass. wait() may collect any eligible child, not necessarily the intended one; waitpid() targets the stored PID. WIFEXITED(status) must be true before WEXITSTATUS(status) is used to extract the real exit code — status itself is an encoded value, not the code.

A1·Q6Limited direct execution and OS control

Q: A CPU-bound process makes no system calls and never yields. Why is direct execution useful/unsafe unlimited? What hardware event regains control? Describe the full sequence including privilege change and saved/restored state. Identify one mechanism and one policy.

A: Direct execution avoids OS interpretation overhead but unlimited direct execution risks privileged ops, protected-memory access, or a CPU held forever. A timer interrupt regains control regardless of cooperation. Sequence: hardware stops the process, saves user context, raises privilege to kernel mode, jumps to the timer handler; OS may invoke the scheduler; if switching, context-switch code saves the current process's context and restores the next one's; return-from-trap lowers privilege and resumes the selected process. Mechanisms: timer interrupt, context switch. Policy: which ready process the scheduler picks next.

Assignment 2 Ch 7 — Scheduling

A2·Q1FIFO, SJF, and turnaround time

Q: A(12ms), B(3ms), C(5ms), all arrive t=0. Compute FIFO and SJF timelines/turnarounds; explain the difference.

A: FIFO (A,B,C order): 0–12 A, 12–15 B, 15–20 C → turnarounds 12,15,20 → avg 15.67ms. SJF: 0–3 B, 3–8 C, 8–20 A → turnarounds 20,3,8 → avg 10.33ms. FIFO forces short jobs behind the long one purely by arrival order — the convoy effect; SJF finishes short jobs early, lowering the average.

A2·Q2Late arrivals and preemption

Q: A(t=0,14ms), B(t=4,3ms), C(t=6,2ms). Compute non-preemptive SJF vs. STCF timelines, turnaround, and response.

A: SJF: 0–14 A, 14–16 C, 16–19 B → turnaround 14/19/10, response 0/12/8. STCF: 0–4 A, 4–7 B, 7–9 C, 9–19 A → turnaround 19/3/3, response 0/0/1. Avg turnaround improves 13→8.33ms; avg response improves 6.67→0.33ms. STCF requires OS preemption support (timer interrupts + context switches).

A2·Q3Round Robin and the time quantum

Q: A(7),B(4),C(6)ms, t=0, RR q=3ms. Timeline, response/turnaround, effect of a much smaller quantum, and behavior as quantum grows past every job's demand.

A: Timeline: 0-3 A,3-6 B,6-9 C,9-12 A,12-13 B,13-16 C,16-17 A. Responses 0/3/6; turnarounds 17/13/16. Smaller quantum → better responsiveness but more frequent context switches (more overhead). Quantum larger than every job's demand → each finishes in its first turn → degenerates to FIFO order.

A2·Q4Context-switch cost and I/O overlap

Q: A,B,C = 4ms each, RR q=2ms, 1ms switch cost. Timeline for first cycle + useful-vs-switching %; a scenario where A alternates 2ms CPU / 5ms I/O — how overlap helps; why adding switch cost changes both turnaround and response, more for short jobs.

A: 0-2 A, 2-3 switch, 3-5 B, 5-6 switch, 6-8 C → 8ms total, 6ms useful (75%), 2ms switching (25%); a 1ms quantum drops useful work to 60%, approaching 50/50 in steady state. With overlap, the CPU runs B/C while A's I/O device works in parallel instead of sitting idle — improving total completion time (the core multiprogramming benefit). Fixed switch cost is a bigger fraction of a short job's total demand, so it hits short jobs' turnaround/response harder.

A2·Q5Workload assumptions and policy selection

Q: W1 = hundreds of short interactive requests (1–5ms); W2 = three long batch jobs, no interactive users. SJF's optimality assumptions, which W1 violates; recommended policy for each; two problems with "RR at 1ms quantum is always best."

A: SJF assumes simultaneous arrival + known lengths — W1 violates both (continuous unpredictable arrivals, unknown request lengths). W1 → Round Robin (response time is what matters for interactive users). W2 → SJF or FIFO (average turnaround / low overhead matters; a convoy effect is still possible even with only three jobs). Problems with "always RR@1ms": (1) fairness ≠ performance — RR can hurt batch turnaround; (2) a 1ms quantum causes frequent switches whose cost depends on the actual switch overhead, which isn't stated, so throughput loss can't be assumed away.

A2·Q6Comparing policies on one workload

Q: A,B,C = 5ms each, t=0. FIFO/SJF/RR(q=1) timelines and average turnaround; why FIFO=SJF here; RR response times vs FIFO's; can one policy be optimal for both metrics?

A: FIFO and SJF are identical (equal demands → tie broken by arrival order) → avg turnaround 10ms each. RR(q=1) avg turnaround 14ms, but avg response 1ms vs FIFO's 5ms. RR wins responsiveness; FIFO wins turnaround — the fundamental tradeoff. Yes, one policy can be optimal for both in special cases (e.g. a single-job workload) — the objectives only conflict once jobs compete.

A2·Q7STCF with multiple arrivals

Q: A(t=0,8ms), B(t=2,4ms), C(t=4,1ms), D(t=5,3ms), STCF. Full timeline, turnaround/response; why C preempts B (not A) at t=4; identify A's preemption points and why STCF still worsens A's own turnaround even though it improves the average.

A: Timeline: 0-2 A, 2-4 B, 4-5 C, 5-7 B, 7-10 D, 10-16 A. Turnarounds 16/5/1/5, avg 6.75ms; responses 0/0/0/2, avg 0.5ms. At t=4, C (1ms remaining) beats B (2ms remaining) — STCF compares remaining time, not arrival order. A is preempted only once, at t=2 by B (a common misreading assumes two preemptions — check this carefully). A's own turnaround worsens (8ms under FIFO → 16ms under STCF) even though the average drops, because STCF repeatedly favors shorter newcomers over the long job already running.

A2·Q8The turnaround-response tradeoff

Q: A and B, 10ms each, t=0. FIFO vs. RR(q=1) averages; why RR's turnaround is worse despite better response; why neither pure FIFO nor pure RR satisfies mixed interactive+batch goals.

A: FIFO: avg turnaround 15ms, avg response 5ms. RR(q=1): avg turnaround 19.5ms, avg response 0.5ms. Under RR neither job finishes early — both are stretched out sharing every millisecond — trading earlier completion for earlier first service. Pure FIFO can strand interactive users behind batch jobs (bad response); pure RR can degrade batch turnaround via constant interleaving. A better scheduler needs to infer job behavior, prioritize short/interactive work for prompt service, and still prevent long-job starvation (aging, priority boosts, etc.).

P1.0The big picture first

proclab's job, per child, in one sentence: create a child, have it become a specific worker program, wait until that worker has definitely finished (and prove it), then collect its result.

Required output comes in three grouped passes, each in increasing index order: every SPAWN line, then every ZOMBIE line, then every REAP line, then one DONE line. That grouping is the reason the code is structured as separate loops/functions rather than doing everything for child 0, then everything for child 1, etc. — the program builds all the children first, then confirms all of them are zombies, then reaps all of them.

P1.1Setup: constants, the Child struct, and why stdout is unbuffered

#define MAX_CHILDREN 20
#define ZOMBIE_TIMEOUT_MS 2000
#define POLL_INTERVAL_MS 5
#define WORKER_PATH "./proclab-worker"
#define WORKER_NAME "proclab-worker"

typedef struct {
    pid_t pid;
    int expected_exit;
} Child;

The Child struct is just a small record the parent keeps for itself, one per child — separate from (and much simpler than) the kernel's own PCB for that process. It remembers two things the parent will need later: the child's PID (so it can target that exact process later) and the expected exit code (so it can double check the worker actually returned what it was told to).

setvbuf(stdout, NULL, _IONBF, 0);

This line turns off stdout buffering entirely (_IONBF = "no buffering"). Why it matters: normally C buffers output and only flushes it at certain points, which can reorder when text actually appears versus when you called printf(). Since proclab's correctness is judged by the exact order lines appear on screen, unbuffered output guarantees each printf() shows up immediately, in the order it was called — no surprises from buffering.

P1.2parse_child_count() — validating N

long value = strtol(text, &end, 10);
if (errno != 0 || end == text || *end != '\0' ||
    value < 0 || value > MAX_CHILDREN) {
    return 0;
}
*count_out = (int)value;
return 1;

This rejects anything that isn't a clean base-10 integer from 0–20. Each check catches a specific bad input:

  • errno != 0 — strtol sets this if the number overflowed a long.
  • end == text — strtol didn't advance at all, meaning the string didn't start with a number (e.g. "abc").
  • *end != '\0' — there's leftover text after the number (e.g. "3x" parses 3 but leaves "x" unconsumed) — this is why the study guide calls out that plain atoi() would be too forgiving here; atoi("3x") silently returns 3 with no way to detect the junk.
  • value < 0 || value > MAX_CHILDREN — enforces the assignment's 0–20 range.

P1.3read_proc_stat() — reading one child's kernel-tracked state

Plain English: this function's whole job is: "given a PID, ask the kernel — via the /proc filesystem — what that process is currently named and what state it's in." It's how proclab checks, from user space, whether a specific child has become a zombie yet.
snprintf(path, sizeof(path), "/proc/%ld/stat", (long)pid);
FILE *file = fopen(path, "r");
fgets(line, sizeof(line), file);

Every running process on Linux gets a virtual file at /proc/<pid>/stat, maintained by the kernel itself (not a real file on disk). This builds that exact path for the child's PID and reads its one line of content.

char *left_paren = strchr(line, '(');
char *right_paren = strrchr(line, ')');
...
size_t name_length = (size_t)(right_paren - left_paren - 1);
memcpy(name, left_paren + 1, name_length);
name[name_length] = '\0';
*state = right_paren[2];

The line looks like 1234 (proclab-worker) Z 1233 ... — the process name is always wrapped in parentheses, which matters because a process name can itself contain spaces or odd characters, so you can't just split on whitespace. The code finds the first ( and the last ) (using strrchr, search-from-the-right) specifically to be safe even if the name itself contained a ). Everything between those parens is the name; the single character two positions after the closing paren (past the paren, past the space) is the state letter — R, S, or the one proclab is hunting for: Z.

Every step returns -1 on any failure (can't build the path, can't open the file, can't read a line, malformed content) rather than crashing — the caller (wait_for_zombies) treats a -1 here as simply "not confirmed yet, try again next poll," which matters because a child might not have a /proc entry ready the very first instant after fork().

P1.4wait_for_zombies() — proving every child is a zombie, on a timeout

Plain English: instead of guessing "the children are probably done by now" with a fixed sleep(), this function keeps checking /proc in a loop, in short bursts, until it has actual evidence — or gives up after ~2 seconds so the program can't hang forever.
int zombie[MAX_CHILDREN] = {0};
int remaining = count;

while (remaining > 0) {
    for (int i = 0; i < count; ++i) {
        if (zombie[i]) continue;                 // already confirmed — skip
        if (read_proc_stat(...) == -1) continue; // not ready yet — try later
        if (strcmp(name, WORKER_NAME) == 0 && state == 'Z') {
            zombie[i] = 1;
            --remaining;
        }
    }
    if (remaining == 0) break;
    // ...check elapsed time against ZOMBIE_TIMEOUT_MS, else...
    nanosleep(&sleep_time, &sleep_time);          // wait ~5ms, then poll again
}

Walk through the logic: zombie[] is a scoreboard, one flag per child, tracking who's confirmed so far. Each pass through the outer while loop sweeps every unconfirmed child once, checking two things together — the process name really is proclab-worker (so it isn't reading stale/wrong data) and its state is Z. Only when both are true does it mark that child confirmed and decrement remaining.

If any children are still unconfirmed after a full sweep, it checks the elapsed wall-clock time (via clock_gettime(CLOCK_MONOTONIC, ...) — monotonic specifically because it can't be affected by the system clock being adjusted mid-run) against the 2-second timeout, and if there's still time left, sleeps ~5ms (nanosleep) before sweeping again. This loop-sleep-loop pattern is the "bounded polling" the study guide describes — bounded because it has a hard timeout, unlike an unconditional single sleep() that proves nothing.

for (int i = 0; i < count; ++i) {
    printf("ZOMBIE index=%d pid=%ld name=%s state=Z\n", ...);
}

Only after the while loop exits with every child confirmed does it print the ZOMBIE lines — in one final pass, in index order. This is the piece that guarantees the required output grouping (all ZOMBIE lines together, in order) regardless of which child actually became a zombie first in real time.

P1.5reap_children() — collecting each child's real result

do {
    result = waitpid(children[i].pid, &status, 0);
} while (result == -1 && errno == EINTR);

Calls waitpid() targeted at this specific child's PID — not bare wait() — because output must be produced in index order, and only waitpid() lets you say "I want this one, specifically." The surrounding do/while retries automatically if the call was interrupted by a signal (EINTR) rather than treating that as a real failure — a real-world robustness detail, not a Ch5 concept itself.

if (!WIFEXITED(status)) { ...fail... }
if (WEXITSTATUS(status) != children[i].expected_exit) { ...fail... }
printf("REAP index=%d pid=%ld exit=%d\n", i, (long)children[i].pid, WEXITSTATUS(status));

This is the decode step from Ch 5.5, applied exactly as it should be: check WIFEXITED(status) first (did it exit normally, as opposed to being killed by a signal?) — only if that's true does it make sense to call WEXITSTATUS(status) to pull out the real exit code. It then double-checks that code matches the expected_exit stored back when the child was created (10 + index), which is how proclab confirms the whole fork→exec→exit chain actually worked correctly for that child, not just that a process exited.

P1.6The fork/exec branch in main() — the core of Ch 5 + Ch 6 in six lines

pid_t pid = fork();
if (pid == -1) {                          // fork itself failed
    fprintf(stderr, "fork failed: %s\n", strerror(errno));
    cleanup_children(children, created);  // reap whoever was already made
    free(children);
    return 1;
}
if (pid == 0) {                           // ---- child branch ----
    char exit_code[12];
    snprintf(exit_code, sizeof(exit_code), "%d", expected_exit);
    execl(WORKER_PATH, WORKER_NAME, exit_code, (char *)NULL);
    dprintf(STDERR_FILENO, "exec failed: %s\n", strerror(errno));
    _exit(127);                           // only reached if execl() FAILED
}
children[i].pid = pid;                    // ---- parent continues here ----
children[i].expected_exit = expected_exit;
++created;

Notice the three-way branch matches Ch 5.1 exactly: pid == -1 is the error case, pid == 0 is the child, and falling through past the if (pid == 0) block (without a matching else!) is the parent's path — the parent never enters that if body at all, since its own fork() call returned the child's PID, not 0.

Inside the child branch: it converts the expected exit code to a string (execl's arguments must be strings, even numeric-looking ones), then calls execl(). If that succeeds, this process image is replaced by proclab-worker and none of the code below execl() ever runs — the process is now running entirely different code. The dprintf + _exit(127) lines only execute if execl() failed and returned control back — which is exactly Ch 5.2's rule that code after a successful exec is unreachable, so anything after it is unambiguously the failure path. And it's _exit(), not exit(), specifically because this is a forked child that inherited the parent's stdio buffers — _exit() skips flushing them and avoids duplicating output the parent will also eventually flush.

P1.7cleanup_children() — surviving a partial failure

static void cleanup_children(Child *children, int count) {
    for (int i = 0; i < count; ++i) {
        waitpid(children[i].pid, &status, 0);   // reap, ignore the exit code
    }
}

This is deliberately simpler than reap_children() — it doesn't check WIFEXITED/WEXITSTATUS or print anything, because its only job is damage control: if something failed partway through creating children (say, child #4's fork() failed after 0–3 already exist), the parent must still collect the children that did get created before the program exits, so no zombies or running processes are left behind when proclab quits early. This is Ch 5.8's "cleanup on partial failure" rule made concrete — and it's called from the fork() == -1 error path and from the "zombies never showed up" timeout path in main().

P1.8main() — how all the pieces are sequenced

  1. Unbuffer stdout.
  2. Validate argv[1] with parse_child_count() — bad input prints usage to stderr and returns 1 immediately.
  3. N == 0 is a special case: print DONE spawned=0 reaped=0 and exit — there's nothing to fork.
  4. malloc() the Child array; a failed allocation is reported and the program exits (nothing to clean up yet, since no children exist).
  5. Loop 1 — create every child, using the fork/exec branch from P1.6, tracking created as it goes so a mid-loop failure knows exactly how many need cleanup.
  6. Loop 2 — print every SPAWN line, in index order, only after every child in loop 1 has actually been created.
  7. Call wait_for_zombies() once, for all children together — on failure (timeout), clean up whoever was created and exit 1.
  8. Call reap_children() once, for all children — on failure, exit 1 (no further cleanup needed; every child was already reaped, successfully or not, inside that loop).
  9. Print the single DONE spawned=N reaped=N line, free the array, return 0.
Why it's split into these exact stages (rather than doing fork→exec→observe→reap for one child at a time, in a single loop): the required output format demands all SPAWN lines, then all ZOMBIE lines, then all REAP lines. That's only possible if every child is created before any observation starts, and every child is confirmed a zombie before any reaping starts — which is exactly why the code is organized as separate sequential passes instead of one combined per-child loop.

P1.9Why output is still deterministic, despite the scheduler being unpredictable (Ch 6 + Ch 7)

The OS scheduler (Ch 7) decides which child — or the parent — actually gets the CPU at any given instant, and proclab has zero control over that interleaving; a re-run of the exact same binary can schedule children in a completely different order. What is under proclab's control is when it looks: it never assumes a child has reached any particular state, it polls /proc and waits for real confirmation (a trap into the kernel, Ch 6) before acting on it. That's the entire trick behind why the printed output is 100% reproducible even though the underlying execution order is not: explicit synchronization replaces any assumption about ordering.

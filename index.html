Advanced Scheduling and Virtual Memory

Everything the Exam 2 study guide lists, rebuilt from the OSTEP chapters, both slide sets, A3, A4 and your P2 code. Each chapter page ends with true/false traps. The practice exam reshuffles every time you start it.

Exam format

Combinational multiple choice

A setup (statement, numeric example or case study), then three or four statements labelled A–D, then four or five answer choices such as “A and B”, “B, C, and D” or a single letter.

Judge every statement on its own as true or false, then pick the choice that matches your evaluation exactly. Partial credit is possible but don't count on it.

Code assembly

Labelled code blocks; you select and order the ones that produce correct P2-like behavior. Some blocks are unused and some are near-duplicates with one important difference. Partial credit for most correct blocks in the right order.

Likely targets: pick a free block, split, free and coalesce, GET, PUT, FIFO or clock victim, retry allocation after eviction.

Write down intermediate stateQueue positions, pass values, free blocks, address fields, page-table entries, TLB contents, resident pages. Every trace on the exam rewards showing each step.

OSTEP Chapter 8

Multi-Level Feedback Queue

SJF gives great turnaround but needs job lengths. Round Robin gives good response but poor turnaround. MLFQ gets both reasonably well by watching what jobs actually do.

Structure

  • Several queues, each a priority level. A ready job sits in exactly one queue.
  • The scheduler runs from the highest-priority non-empty queue; jobs at the same level share the CPU in Round Robin.
  • Quantum = most CPU time in one dispatch. Allotment = total CPU budget at one level before demotion.

The five reference rules

#RuleWhy
1If Priority(A) > Priority(B), A runs.Favor urgent work
2If Priority(A) = Priority(B), A and B run in RR.Share among peers
3New jobs enter at the highest priority.Assume a job is short until it proves otherwise
4Once a job uses its total allotment at a level, it is demoted, regardless of how many times it gave up the CPU.Classify CPU use; prevent gaming
5After period S, move all jobs to the top queue.Bound starvation; re-evaluate jobs whose behavior changed

How the rules evolved (a source of trick statements)

  • Old Rule 4a: use a whole time slice → move down. Old Rule 4b: give up the CPU before the slice ends → stay at the same level.
  • Problem 1, starvation: if interactive jobs keep the top queue busy, demoted jobs never run. They also can't show that their behavior changed.
  • Problem 2, gaming: with 4b, a job runs 99% of a slice, does trivial I/O, and keeps top priority with its usage reset.
  • Problem 3, changing behavior: a CPU-bound phase can turn interactive later.
  • Rule 5 (boost) fixes starvation and changing behavior. The rewritten Rule 4 (cumulative accounting across yields) fixes gaming.

Why it works

  • Approximates SJF: short jobs finish before being demoted far; long CPU-bound jobs reveal themselves by consuming allotment and sink.
  • Interactive jobs stay high: short bursts then blocking for I/O use the allotment slowly, so prompt response continues.
  • Lower queues often get longer quanta (e.g. 8 / 16 / 64 ms or 10 / 20 / 40 ms): CPU-bound work switches less and keeps cache/TLB state. This is a design choice, not a universal rule.
  • Solaris TS class: 60 queues, 20 ms at top to a few hundred ms at bottom, boost about every 1 s.

Limits

  • MLFQ balances turnaround and response; it does not guarantee any job a specific CPU share. That needs a different objective (Chapter 9).
  • It cannot know the future, so it approximates SJF but cannot guarantee the exact SJF schedule.
  • Parameters (number of queues, quanta, allotments, S) are workload-sensitive. Too long an S starves; too short an S hurts interactive jobs.

OSTEP Chapter 9

Proportional-share scheduling

A different objective: divide CPU time according to explicit weights, not minimize turnaround or response.

Tickets

  • Tickets are resource rights. Target share = your tickets ÷ all runnable tickets. Only ratios matter: doubling every count changes nothing.
  • When a job arrives, exits or changes its count, the denominator changes and every target adjusts. A 300 / 100 / 100 split gives 60% / 20% / 20%; if C exits, A gets 300/400 = 75%.
  • Currency: a user splits a local budget; the system converts to global. User A holds 100 global and gives A1 and A2 500 each of A's currency → 50 global each. User B gives B1 10 of B's currency → all 100 of B's global.
  • Transfer: a client temporarily hands tickets to a server working for it. Inflation: a trusted process raises or lowers its own count (unsafe among untrusted processes).

Lottery scheduling

  • Each quantum, draw a random winner in [0, total) and run its owner. Implementation: walk the job list adding ticket counts until the running total exceeds the winner.
  • A owns 0–74 and B owns 75–99: draw 62 → A, draw 74 → A, draw 75 → B.
  • Fairness is probabilistic. 75% of tickets does not mean 75 of every 100 wins. Short runs can deviate badly; long runs converge.
  • Unfairness U = (finish time of first job) ÷ (finish time of second). Two 10 ms jobs finishing at 10 and 20 → U = 0.5. U → 1 as jobs get longer.
  • Handles arrivals, exits and ticket changes easily: no accumulated per-job state to repair.

Slide example. A has 0–74, B has 75–99. Winning numbers 63 85 70 39 76 17 29 41 36 39 10 99 68 83 63 map to:

A B A A B A A A A A A B A B A

B won 4 of 15 (27%) even though its target is 25%. Small samples drift.

Stride scheduling

  • stride = large constant ÷ tickets. Always run the runnable job with the smallest pass; after it runs, pass += stride.
  • More tickets → smaller stride → pass grows slower → runs more often.
  • Deterministic, with exact proportions at cycle boundaries. Costs: per-job pass state and a new-arrival problem (a newcomer with pass 0 would monopolize the CPU, so it needs a sensible starting pass such as the current minimum).

CFS-style virtual runtime

  • Run the task with the smallest vruntime; a balanced (red-black) tree keeps tasks sorted, O(log n) insert/remove.
  • vruntime += runtime × default_weight ÷ weight. Higher weight → vruntime grows more slowly per real ms → selected more often.
  • Nice levels map to weights (about 1.25× per level). Niceness is an input to proportional accounting, not a fixed-priority queue.
  • Target latency is divided among runnable tasks; minimum granularity stops slices from getting too small. More switching tracks ideal sharing more closely but costs more overhead.

OSTEP Chapters 13–14

Address spaces and the memory API

Every process behaves as if it owns a large, private, contiguous memory starting at 0. Physical RAM is finite and shared.

Why the abstraction

  • Early systems: one program plus the OS in RAM. Poor utilization.
  • Multiprogramming keeps several processes resident and switches the CPU among them. Saving all of memory to disk on each switch would be far too slow, so processes stay in RAM, which creates the protection problem.

Virtual vs physical

  • Every address a user program sees or prints is virtual. It names a location in that process's view, not a RAM cell.
  • Two processes can both write virtual address 100 and keep different values, because hardware translates each in the context of the running process.
  • A3 example: a process loaded at 320 KB reading virtual 0x0400 does not read physical 0x0400 (that's inside the OS).

Regions

code0 KB, fixed sizestatic dataheap → grows up(free gap)← stack grows down16 KB
  • Code: instructions, fixed size. Static data: lives for the whole run.
  • Heap: explicitly requested, may outlive the call that made it, grows toward higher addresses.
  • Stack: locals, arguments, return addresses for active calls; grows toward lower addresses.
  • Heap and stack grow toward each other into one gap so neither size must be predicted.
Two separate questions“What addresses could this process use?” is about the virtual address space. “How much RAM has the OS committed?” is about physical placement. An unused virtual gap does not necessarily consume the same amount of physical memory.

Three goals

Transparency

The program uses the same addresses wherever it's placed and doesn't know memory is virtualized.

Efficiency

Both time (translation can't slow every access much) and space (bookkeeping can't eat RAM). Needs hardware support; software translation of every access would be far too slow.

Protection

A process can't read or write another process or the OS, even if it's buggy or malicious. Gives isolation: one crash stays contained. “Programmers should just write correct code” is not a defense.

Kinds of memory

  • Stack: allocated and freed automatically by the compiler-generated call/return code. A pointer to a local becomes dangling once the function returns.
  • Heap: malloc(size) returns a pointer or NULL; free(ptr) takes no size (the allocator finds it in a header). calloc zeroes; realloc may move the block.
  • OS level: the OS manages whole address spaces and maps memory to processes (brk/sbrk move the heap's break; programmers shouldn't call them directly). A user-level allocator subdivides space inside the process's virtual address space; it never picks physical frames.
  • On exit, the OS reclaims all of a process's memory, freed or not. The heap allocator's bookkeeping dies with the process.
  • sizeof on a pointer gives the pointer size (e.g. 8), not the allocation; on an array it gives the array size.

Process isolation is not object isolation: hardware stops a process touching another process, but not one of its own objects overflowing into another.

Leaks don't matter much in a short-lived program (the OS reclaims at exit). They become critical in long-running servers and daemons, where the leaked total grows without bound while the process is alive.

OSTEP Chapters 15–16

Address translation and segmentation

Hardware turns each virtual address into a physical one and enforces protection. The OS sets up the hardware at key moments.

Base and bounds (dynamic relocation)

  • Two privileged registers in the MMU. Base = physical start. Bounds = size of the address space (a limit, not a second base).
  • Legal if 0 ≤ VA < bounds. Check first, then PA = base + VA. Illegal → exception, OS handles it.
  • OS duties: at creation find free physical space (free list); at exit reclaim it; on context switch save/restore base and bounds in the PCB. A context switch doesn't copy memory.
  • Registers must be privileged, or a process could point its base at someone else's memory.

Slides: base 32 KB, bounds 16 KB. VA 128 → 32,896. VA 15 KB → 47 KB. VA 16 KB → fault (equal to bounds is outside).

A3: base 0x40000, bounds 0x4000. 0x0000 → 0x40000; 0x1A00 → 0x41A00; 0x3FFF → 0x43FFF; 0x4000 → fault.

Limits

  • The whole address space, including the empty heap–stack gap, occupies one contiguous physical block. The course calls this unused reserved space internal fragmentation.
  • Sparse address spaces waste memory, a space larger than RAM can't run, and you can't share just the code.
  • Across many processes coming and going, base-and-bounds can also leave external holes at the system level (A3 Q12).

Segmentation

  • A base and bound (size) per logical segment: code, heap, stack. Each can sit anywhere in RAM; virtual gaps need no physical memory.
  • Explicit selection: top bits of the VA pick the segment, the rest is the offset. Some systems use an implicit approach (which register formed the address).
  • Extra hardware: a grows-positive bit per segment (stack grows negative) and protection bits (read / write / execute). Code marked read-execute can be shared between processes.
  • Coarse-grained = a few segments; fine-grained = many, needing a segment table.

Translating a segmented address

  1. Split the VA: segment bits | offset bits.
  2. Bounds check the offset against that segment's size.
  3. PA = segment base + offset (grows-down segments: see below).

Fragmentation

External

Enough total free space, but split into non-contiguous holes too small for one request. Free 8 + 4 + 12 = 24 KB can't fit a 20 KB segment; free 1 + 2 + 4 = 7 KB can't fit 6 KB.

Internal

Space inside an allocated unit the requester can't use, from rounding or fixed-size units.

Compaction copies live segments together and updates their bases, turning scattered holes into one. It's expensive: copying memory, pausing affected processes, updating every segment register. Future frees create new holes, so it's a repair, not a solution.

OSTEP Chapter 17

Free-space management

Find one contiguous block, keep the usable remainder, and rebuild larger regions when blocks come back. This is the direct foundation for P2.

The free list

  • Describes available regions by address and length. A 30-byte heap with bytes 10–19 used: head → (0,10) → (20,10) → NULL.
  • A request needs one contiguous region: 20 free bytes can't satisfy a 15-byte request here.
  • List order ≠ physical adjacency. A next pointer gives search order; addresses tell you whether blocks touch.

Splitting and coalescing

  • Split: allocate part of a big enough free block and keep the rest. Take 1 byte at address 20 → (0,10) → (21,9).
  • Create a remainder only if it can hold metadata plus usable payload; otherwise give the small remainder to the allocation.
  • Coalesce: on free, merge with physically adjacent free blocks. Returning 10–19 above merges all three into (0,30). Without merging, three 10-byte entries still can't satisfy 20.
  • Without coalescing the list degrades into many small entries and rejects requests the space could hold.

Embedded metadata

  • The allocator can't call malloc for its own list, so headers and free-list nodes live inside the managed space.
  • An allocated block's header sits just before the returned pointer and holds at least the size (plus a magic number for checks). free(ptr) finds it at ptr − sizeof(header).
  • A request for N bytes consumes N + header bytes.

OSTEP 4 KB example (8-byte header, 8-byte free node):

  • Start: one free node, size 4096 − 8 = 4088.
  • malloc(100) consumes 108 → free chunk 3980.
  • Three malloc(100)s consume 324 → free chunk 3764.
  • Freeing the middle block puts it at the list head; its next points to the 3764 chunk. Don't merge those two: an allocated block sits between them.
  • Free all three without coalescing → four list entries even though the whole region is free.

Requested vs consumed

Know these separately: requested size, rounded (aligned) size, block capacity, header bytes, total pool consumption.

8-byte alignment, 8-byte header, request 13 → payload 16 + header 8 = 24 bytes consumed. The 3 unused payload bytes are internal fragmentation; the header is bookkeeping overhead, counted separately.

OSTEP Chapters 18–19

Paging and TLBs

Fixed-size pages and frames remove external fragmentation. The price is a translation step on every access and large page tables. The TLB fixes the speed problem.

Pages and frames

  • Virtual memory is cut into pages, physical memory into frames of the same size. They belong to different address spaces.
  • Any free frame can hold any page, so external fragmentation disappears. Internal fragmentation remains in the last, partially used page.
  • Page tables are per process (though frames can be shared).

Translating a paged address

VPNhigh bits → which pageoffsetlow log₂(page size) bits
  1. Offset bits = log2(page size); the remaining bits are the VPN.
  2. Look up PTE[VPN] (at PTBR + VPN × sizeof(PTE)). Check valid, then protection.
  3. Replace VPN with PFN; keep the offset unchanged. PA = PFN × page size + offset.

OSTEP: 64-byte space, 16-byte pages, table [3, 7, 5, 2]. VA 21 = 01 0101 → VPN 1, offset 5 → PFN 7 → PA 7 × 16 + 5 = 117.

A4 Q2: 16 KB space, 1 KB pages → 14-bit VA, 10 offset bits, 4 VPN bits. VPN 0→5, 1→8, 4→2, 15→12, rest invalid.

Exact bit layout varies (x86 has P, R/W, U/S, A, D, PFN…). Know the purposes.

Cost of plain paging

  • Space: a linear table has an entry for every possible virtual page. 32-bit VA, 4 KB pages, 4 B PTEs → 220 × 4 B = 4 MB per process; 100 processes → 400 MB.
  • Time: every reference first reads the PTE from memory, then does the real access: two memory accesses. At 100 ns each, an instruction fetch takes 200 ns.

The TLB

  • A small hardware cache in the MMU of recent VPN → PFN translations plus protection bits. Typically 32–128 entries, fully associative, searched in parallel.
  • Hit: form the PA from the cached PFN, no page-table access. Miss: read the PTE from the page table, insert it into the TLB, retry the instruction, which now hits.
  • Hardware-managed TLB (x86/CISC): the MMU walks the table using PTBR. Software-managed (MIPS/RISC): the miss traps to an OS handler, which inserts the entry with a privileged instruction and returns-from-trap to retry.
  • Entry contents: VPN, PFN, valid, protection, ASID, dirty, (MIPS: global, coherence bits).
Critical distinctionA TLB miss means the translation isn't cached. A page fault means the page isn't in physical memory. A TLB miss is usually resolved from the in-memory page table with no disk I/O.

Locality

  • Spatial: touching address x makes nearby addresses likely soon. Temporal: recently used items are likely reused.
  • OSTEP array: 10 four-byte ints, 16-byte pages, a[0] at offset 4 of VPN 6 → pages 6, 7, 8 → 3 misses, 7 hits, 70%. A second pass right after hits 100%.
  • One 4 KB page holds 1024 ints: one miss then 1023 hits (99.9%). A 64-entry TLB with 4 KB pages reaches 256 KB.

Context switches

The same VPN maps to different PFNs in different processes (A: VPN 10 → 100; B: VPN 10 → 170). Without help, B could use A's stale entry. Two fixes:

  • Flush the TLB (set all valid bits to 0) on every switch. Safe, but each switch starts cold.
  • ASIDs: tag each entry with an address-space ID so entries from several processes coexist. Shared pages can appear under different VPNs and ASIDs pointing to one PFN.

Page size tradeoff

  • Larger pages → more TLB reach, fewer PTEs, more internal fragmentation.
  • A4: 256 KB of data = 64 pages at 4 KB vs 4 pages at 64 KB. A 100-byte object wastes 3,996 B in a 4 KB page vs 65,436 B in a 64 KB page.

Effective access time

EAT = h × 101 + (1 − h) × 201 with 1 ns TLB lookup and 100 ns memory.

95% → 0.95 × 101 + 0.05 × 201 = 106 ns · 80% → 121 ns · 50% → 151 ns.

If a question says the TLB lookup cost is negligible: hit = 100, miss = 200.

Multi-level page tables

A linear table pays for the whole possible address space, including huge invalid regions. A tree of page-sized tables pays only for regions in use.

The metadata problem

  • Linear table size scales with the possible virtual space, not the pages in use. A process using 12 KB (4 KB each of code, heap, stack) still needs 220 entries = 4 MB, with 3 valid.
  • Bigger pages shrink the table (16 KB pages → 218 × 4 B = 1 MB) but increase internal fragmentation.
  • Hybrid (paging + segments): one page table per segment, base points to the table, bounds marks its end. Still wasteful for a large sparse heap and brings back external fragmentation of the tables.

The tree

  • Chop the linear table into page-sized pieces. A page directory has one entry (PDE: valid + PFN) per piece.
  • If a whole piece would be invalid, its PDE is invalid and that page of PTEs is never allocated.
  • Each level fits in one page, so the OS can grab any free frame when a table grows.
  • 32-bit, 4 KB pages, 4 B entries: 1024 entries per page → 10 | 10 | 12. A typical small process: 1 directory + 2 table pages ≈ 12 KB instead of 4 MB.

The walk on a TLB miss

  1. PDE = memory[PDBR + PDindex × sizeof(PDE)]. Invalid → segmentation fault.
  2. PTE = memory[PDE.PFN × page size + PTindex × sizeof(PTE)]. Invalid → segmentation fault; protection check.
  3. Insert into TLB, retry. PA = PTE.PFN × page size + offset.

OSTEP Chapters 21–22

Beyond physical memory

When the active pages of all processes don't fit in RAM, the OS keeps some on disk and treats RAM as a cache for them.

Mechanisms

  • Swap space: disk/SSD area holding non-resident pages, tracked in page-sized units (the PTE can hold the disk address when not present).
  • Demand paging: bring a legal page in only when an instruction touches it. (Prefetching can guess ahead; clustering groups pending writes into one large write.)
  • Valid vs present: a page can be legal (valid = 1) yet not in RAM (present = 0).

Hardware path on a TLB miss

  1. Fetch PTE. Valid = 0 → segmentation fault.
  2. Protection fails → protection fault.
  3. Present = 1 → insert into TLB, retry.
  4. Present = 0 → page fault exception.

Page fault handling (OS)

  1. Hardware traps to the kernel.
  2. OS checks the access is valid and finds the page's disk location in the PTE.
  3. Find a free frame; if none, run the replacement policy to evict one (write it back first if dirty).
  4. Issue the disk read. The faulting process blocks; the scheduler runs another ready process.
  5. On I/O completion: set PTE present = 1 and PFN, process becomes ready.
  6. Restart the faulting instruction. It TLB-misses, finds the page present, inserts, retries, and hits.

Disk reads take ~10 ms against ~100 ns for RAM, which is why the CPU is given to someone else meanwhile.

Eviction only when neededA page fault needs an eviction only if no free frame exists. With watermarks, a free frame is usually already waiting.

Dirty bit and watermarks

  • Clean page (dirty = 0, e.g. code): drop it, 1 disk operation for the incoming read. Dirty page: write back first, 2 disk operations.
  • The victim's PTE gets present = 0; the new page's PTE gets present = 1 and the frame's PFN.
  • Swap/page daemon: when free frames fall below the low watermark, a background thread evicts until the high watermark is reached, then sleeps.

Replacement policies

Goal: evict a page unlikely to be needed soon to minimize future misses. AMAT = T_M + P_miss × T_D; with disk this slow, even a small miss rate dominates.

Clock in detail

  • Hardware sets the use bit to 1 on any access; only the OS clears it.
  • Pages form a circle; a hand persists between evictions.
  • At the hand: use = 1 → clear it, advance (second chance). Use = 0 → evict, place the new page there with use = 1, advance.
  • If every bit is 1, the hand sweeps a full circle clearing them and evicts the page it started on (behaves like FIFO for that sweep).
  • Variant: prefer clean unused pages to avoid write-backs.

Worked traces

Belady's anomaly: 1, 2, 3, 4, 1, 2, 5, 1, 2, 3, 4, 5 under FIFO gives 9 faults with 3 frames and 10 with 4.

Replacement tracer

Clock: frames fill in order; a loaded or hit page gets use = 1; the hand starts at frame 0 and only moves while searching for a victim, then steps past the replaced frame. OPT ties evict the lowest frame.

Workloads

  • No locality: all realistic policies perform about the same; when the cache holds everything, the policy doesn't matter.
  • 80-20: LRU keeps hot pages and beats FIFO/Random; clock lands between LRU and FIFO.
  • Looping sequential (50 pages, cache 49): LRU and FIFO miss every time; Random does better.

Working sets and thrashing

  • Working set: the pages a process is actively using during a period.
  • Thrashing: active working sets exceed RAM, so the system spends its time paging instead of running. CPU utilization collapses while disk queues saturate.
  • No replacement policy can create capacity that isn't there. Fixes: run fewer processes (admission control) or kill/suspend some (out-of-memory killer).
P2 connectionP2's FIFO and clock give concrete eviction practice with reference bits. The analogy has limits: P2 evicts variable-sized objects, not fixed-size pages, and a P2 GET miss doesn't cause a page fault or a disk read.

cachelab: placement meets eviction

The most important source for the code-assembly section. Two independent policy choices share one pool.

Placement policy

First fit or best fit chooses where a new variable-sized object goes. It picks a free block.

Eviction policy

FIFO or clock chooses which cached object leaves when no free block fits a PUT. It picks an occupied object.

Evicting an object changes the free-space layout, which changes placement's next decision.

Data structures

typedef struct block_header {
    size_t size;               /* payload capacity, excludes header */
    int free;                  /* 1 when free, 0 when allocated */
    struct block_header *next; /* next block in pool ADDRESS order */
} block_header_t;              /* 24 bytes, 8-byte aligned on a 64-bit build */

#define HEADER_SIZE      (sizeof(struct block_header))
#define MIN_BLOCK_SIZE   (HEADER_SIZE + 1)
#define HEADER_ALIGNMENT (_Alignof(struct block_header))
  • Embedded pool list: every block, free and allocated, in address order. header_from_payload(p) = p − HEADER_SIZE.
  • Cache index: hash table of active entries (index_find / index_insert / index_remove).
  • Policy list: doubly linked list of active entries in insertion order, plus a persistent clock_hand. Separate from the pool list.

Pool invariants

  • The pool begins as one free block: size = pool_size − HEADER_SIZE.
  • Every block = header in the pool + payload capacity. Blocks cover the pool with no gaps or overlap; headers stay aligned.
  • size is payload capacity, not total block bytes and not the requested object size.
  • A split puts the allocation at the front and a new aligned header for the remainder right after the rounded payload.
  • Split only if the remainder holds a header plus at least one payload byte (size − physical ≥ MIN_BLOCK_SIZE); otherwise the allocation absorbs it.
  • Freeing marks the block free and coalesces free successor and predecessor. No two adjacent free blocks remain after pool_free().
  • Total free bytes don't matter if no single contiguous free block is large enough.

Pool code (your implementation)

static block_header_t *first_fit(memory_pool_t *pool, size_t requested) {
    for (block_header_t *cur = pool->blocks; cur; cur = cur->next)
        if (cur->free && cur->size >= requested) return cur;
    return NULL;
}
static block_header_t *best_fit(memory_pool_t *pool, size_t requested) {
    block_header_t *best = NULL;
    for (block_header_t *cur = pool->blocks; cur; cur = cur->next)
        if (cur->free && cur->size >= requested && (!best || cur->size < best->size))
            best = cur;          /* strict < keeps the earliest of equal sizes */
    return best;
}
static void split_if_possible(block_header_t *block, size_t requested) {
    size_t physical = round_up(requested, HEADER_ALIGNMENT);
    if (physical > block->size || block->size - physical < MIN_BLOCK_SIZE) return;
    block_header_t *rest = (block_header_t *)((unsigned char *)payload_from_header(block) + physical);
    rest->size = block->size - physical - HEADER_SIZE;
    rest->free = 1;
    rest->next = block->next;   /* must happen before block->next changes */
    block->size = physical;
    block->next = rest;
}
void *pool_try_alloc(memory_pool_t *pool, size_t requested) {
    block_header_t *block = pool->policy == ALLOC_BEST_FIT ? best_fit(pool, requested)
                                                          : first_fit(pool, requested);
    if (!block) return NULL;
    split_if_possible(block, requested);
    block->free = 0;
    return payload_from_header(block);
}
void pool_free(memory_pool_t *pool, void *payload, event_context_t *ev) {
    block_header_t *block = header_from_payload(payload);
    block->free = 1;
    if (block->next && block->next->free) {            /* successor */
        block_header_t *succ = block->next;
        block->size += HEADER_SIZE + succ->size;          /* recover succ's header */
        block->next = succ->next;                         /* COALESCE event */
    }
    block_header_t *prev = NULL, *cur = pool->blocks;   /* predecessor */
    while (cur && cur != block) { prev = cur; cur = cur->next; }
    if (prev && prev->free) {
        prev->size += HEADER_SIZE + block->size;
        prev->next = block->next;                         /* COALESCE event */
    }
}

Because the P2 list holds every block in address order, block->next and the walked prev are true physical neighbors. In a free-only list (Ch 17), list neighbors are not necessarily adjacent.

Cache invariants

  • The index and the policy list contain exactly the active entries.
  • GET hit: set the reference bit, count a hit. Nothing else.
  • GET miss: count a miss. No allocate, free, evict, FIFO reorder or clock-hand move.
  • An impossible PUT (size > pool.size − HEADER_SIZE) is rejected before touching an existing entry with the same key.
  • A valid PUT for an existing key is an UPDATE, not an eviction: remove the old entry from index and policy list, subtract its occupancy, free its block, then place the new one.
  • A PUT tries allocation first. If nothing fits: select one victim, evict it (remove + free), retry. Repeat until allocation succeeds; one eviction may not be enough.
  • A successful PUT is a new insertion at the policy tail with reference bit = 1.
  • Occupancy counts requested payload sizes, not headers, padding, block capacity or absorbed remainders.

static void evict_one(cache_t *cache, cache_entry_t *victim, event_context_t *ev) {
    /* EVICT event */
    index_remove(cache, victim);
    policy_remove(cache, victim);              /* also repairs clock_hand */
    cache->occupancy -= victim->requested_size;
    cache->evictions++;
    pool_free(&cache->pool, victim->payload, ev);
}
void handle_get(cache_t *cache, request_t *req, event_context_t *ev) {
    cache_entry_t *entry = index_find(cache, req->key);
    if (entry) { entry->reference_bit = 1; cache->hits++;   /* HIT */ }
    else       { cache->misses++;                           /* MISS */ }
}
void handle_put(cache_t *cache, request_t *req, event_context_t *ev) {
    /* PUT event */
    if (req->size > cache->pool.size - HEADER_SIZE) {       /* REJECT first */
        cache->rejects++; return;
    }
    cache_entry_t *old = index_find(cache, req->key);
    if (old) {                                               /* UPDATE */
        index_remove(cache, old);
        policy_remove(cache, old);
        cache->occupancy -= old->requested_size;
        pool_free(&cache->pool, old->payload, ev);
    }
    void *payload = pool_try_alloc(&cache->pool, req->size);
    while (!payload) {
        cache_entry_t *victim = cache->eviction_policy == EVICT_CLOCK
                                ? evict_clock_select(cache) : evict_fifo_select(cache);
        evict_one(cache, victim, ev);
        payload = pool_try_alloc(&cache->pool, req->size);
    }
    cache_entry_t *entry = &req->entry_storage;
    strcpy(entry->key, req->key);
    entry->requested_size = req->size;
    entry->payload = payload;
    entry->reference_bit = 1;
    index_insert(cache, entry);
    policy_append(cache, entry);
    cache->occupancy += req->size;                           /* requested, not capacity */
    /* ALLOC event */
}

Provided helpers: policy_append sets clock_hand on the first append and doesn't move it afterwards. policy_remove advances the hand if it pointed at the removed entry (or sets it NULL if the list empties). policy_successor wraps from tail to head. No locking inside handlers: the worker already holds cache_lock then output_lock for the whole request.

Clock in P2

  • PUT and successful GET set an entry's bit. Clock clears a set bit and advances (second chance); it selects an entry whose bit is clear.
  • Because every new entry starts with bit 1, a cache of only fresh entries makes the first sweep clear everything and return to the entry where the hand started.
  • The hand persists. Resetting it to the head on every search is a bug.
  • The selector only selects. evict_one unlinks; unlinking in the selector too removes the victim twice.

Example. Policy list a, b, c; hand at a; bits a = 1, b = 0, c = 1 (b was inserted, then the hand cleared it on an earlier sweep, and no GET touched it since). Clock select: a has 1 → clear, hand → b. b has 0 → select b; hand already moved to c. evict_one(b) unlinks b; hand stays at c.
